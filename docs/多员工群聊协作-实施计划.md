## 0. 核实结论（先看这个）

设计文档对代码的判断**全部属实**。一处关键利好文档未充分利用：

> **完成事件的钩子已经存在。** `stream_registry.py:1415` 在每个流终态化时回调 `registry.on_task_finalized(...)`，并已挂在 `server.py:129` 的 `_on_task_finalized`。该回调**已携带** `task_id` / `workspace_id` / `execution_log_id` / `orchestrator_conversation_id`。
>
> 因此"完成驱动调度器"**不需要从零写事件监听**——只需在现有 `_on_task_finalized` 的 `stream_state=="completed"` 分支里追加"完成才递减依赖→派后继"。这把文档评的"高风险核心新逻辑"实际降到**中风险**。

## Phase 0 · 验证假设（1–2 天，不写功能，但决定路线 A 是否成立）

路线 A 的卖点是"员工×员工真并行"。代码里这条**从未被验证**——必须先压测，否则后面全是空中楼阁。

### 0.1 已知风险点（代码证据）

| 风险 | 证据 | 说明 |
|---|---|---|
| LangGraph 并发串流冲突 | `execution.py:33` 注释 + `:38-76` `_start_employee_stream_when_orchestrator_idle` | 代码**只确认过总管×员工**的 `astream(stream_mode="messages")` 冲突，靠"等总管 idle"规避。员工×员工是**默认假定安全**，未验证。 |
| SQLite 全局写锁 | `runtime.py:24` `SQLITE_ACCESS_LOCK` | 所有 orchestrator DB 写入串行化。N 个员工并行 flush checkpoint + 写消息会在这把锁排队，**真并行天花板可能是这把锁，不是 llama.cpp `-np 4`**。 |
| 每员工并发上限 | `runtime.py:17,222` `MAX_CONCURRENT_PER_EMPLOYEE=2` | 同一员工最多 2 个并发任务（按 `TaskExecutionLog.run_status in (running,queued)` 计数）。不同员工互不阻塞。 |

### 0.2 压测动作

1. 构造一个无依赖的双任务计划（两个**不同员工**），走 `execute_plan` → `start_immediate_tasks`。
2. 观察：两个 `registry.start` 是否都进 active（`stream_registry.py:415` `count_active_streams`），还是有一个被拒/排队。
3. 监控 `SQLITE_ACCESS_LOCK` 争用（在 `orchestrator_sqlite_guard` 加临时计时日志）。
4. 验证两路 astream 的 token 不串台（前端两条会话各自只收自己的 chunk）。

**验收**：双员工并行 astream 完整跑完、消息不串台、无死锁。**若失败**→路线 A 需要给员工×员工也加串流隔离（代价上升，需重新评估）。

## Phase 1 · 完成驱动调度器（核心价值，可独立交付，不依赖"房间"）

修掉 I6 的"伪 DAG"。**这一步单独就能让现有串行编排真正工作**，建议优先交付。

### 1.1 问题锚点

`execution.py:206-218`：任务一 `start` 就立即给后继 `dep_count -= 1`，减到 0 当场进 `ready_ids` 并在**同一循环**里启动。结果 B 在 A **刚启动**时就被派出，A 的产出根本没出来。

```
# execution.py:214-218 (当前 BUG)
for other_id, other_deps in dep_map.items():
    if task.id in other_deps:
        dep_count[other_id] = dep_count.get(other_id, 0) - 1   # ← start 即递减
        if dep_count[other_id] <= 0:
            ready_ids.add(other_id)                            # ← 当场就绪
```

### 1.2 改造方案

**思路**：`start_immediate_tasks` 只派**当前无依赖**的任务（dep_count==0），**删掉 start 时的递减**。把"递减→派后继"搬到完成回调里触发。

#### 改动 1 — `execution.py:start_immediate_tasks`
- 删除 `:214-218` 的 start-时递减块。
- 函数只负责派出 `dep_count==0` 的根任务。
- 把依赖关系（`dep_map` / `dep_count`）**持久化**，供完成回调读取。
  - 最小做法：依赖已经在 `plan_json` 里（`plan.plan_json`，`:157`），完成回调可重新 `json.loads` 计算"谁依赖刚完成的任务"。无需新表。
  - 需要一个"task 索引 ↔ task.id"的映射；`plan_json_obj[i]` 的顺序对应 `tasks[i]`（`:162`），完成回调按同样顺序重建即可。

#### 改动 2 — 新增 `on_employee_task_completed(task_id, workspace_id)`（`execution.py` 内）
完成驱动的核心，由完成回调调用：
```
当某员工任务 task_id 完成时：
    1. 查 TaskExecutionLog → 拿到 plan_id（经 EmployeeTask.orchestration_plan_id）
    2. 重建该 plan 的 dep_map / 当前未启动任务
    3. 对所有"依赖 task_id"且尚未启动的后继 n：dep_count[n] -= 1
    4. dep_count[n]==0 且 n 未启动 → start_task_as_conversation(n)
       （派 n 时，把前置产物的"地址/引用"拼进 user_prompt —— 见 1.4）
```
> 注意并发：多个前置同时完成会并发调这个函数，递减要在 `SQLITE_ACCESS_LOCK` 下做，或用乐观计数（按 DB 中"已完成的前置数 vs 总前置数"判断，而非内存计数器，避免重启丢状态）。**推荐用 DB 派生计数**——更健壮。

#### 改动 3 — 接入现有完成回调 `server.py:95-129`
在 `_on_task_finalized` 的 `stream_state == "completed"` 分支（`:112-116`）**追加**调用（不替换现有 UI 事件推送）：
```python
if stream_state == "completed":
    WorkspaceEventBus.push(workspace_id, {"type": "task_completed", **base})
    # ↓ 新增
    from src.service.agent.orchestrator.execution import on_employee_task_completed
    on_employee_task_completed(task_id, workspace_id)
```
> 该回调在 `stream_registry.py:1415` 的 DB 上下文里被调，注意用独立 Session（参考 `runtime.py:235` `get_session_local()()` 的写法）避免复用已 close 的会话。

### 1.3 多依赖支持（`int` → `int[]`）

#### 改动 4 — `execution.py:165-169`
```python
# 当前：仅单 int
if isinstance(raw, int):
    dep_task = tasks[raw] if raw < len(tasks) else None
    if dep_task and dep_task.id in task_lookup:
        deps = [dep_task.id]
```
改为同时接受 `int` 和 `list[int]`：
```python
raw_list = raw if isinstance(raw, list) else ([raw] if isinstance(raw, int) else [])
for idx in raw_list:
    dep_task = tasks[idx] if isinstance(idx, int) and idx < len(tasks) else None
    if dep_task and dep_task.id in task_lookup:
        deps.append(dep_task.id)
```

#### 改动 5 — 提示词契约 `plans.py:45` 与 schema `schemas/orchestration.py:22`
- `plans.py:45` `"depends_on": <int | null>` → `<int | int[] | null>`，并在描述里说明多依赖含义。
- `schemas/orchestration.py:22` `depends_on: int | None` → `int | list[int] | None`（向后兼容）。

### 1.4 前置产物交接（只传引用，不塞上下文）

派后继任务 n 时，在其 `user_prompt` 后追加前置产物的**路径/引用**（不是全文）：
- 前置产物落在 `settings.artifacts_path`（`execution.py:340`）。
- 后继简报里给"前置 X 的产物在 `<artifacts_path>/...`，请自行读取"。
- 对齐设计文档 §8 坑①（防上下文爆炸）与 ChatDev"只传结论"。

### Phase 1 验收
- 构造 A→B 依赖计划：B 必须在 A 的 `stream_state` 变 `completed` **之后**才创建会话（看 `task_started` 事件时间戳）。
- B 的 prompt 里能拿到 A 的产物引用。
- 多依赖 A,B→C：C 等 A、B 都完成才起。
- 单 int `depends_on` 的旧计划仍能跑（向后兼容）。

## Phase 2 · 房间数据模型 + 投影

让协作"看得见"。Phase 1 完成后才做。

### 2.1 数据模型（扩展，不砸现有表）

新增（设计文档 §6.1）：
```
group_room        { id, workspace_id, plan_id, leader_conversation_id, status, created_at }
group_room_member { room_id, conversation_id, employee_id,
                    role_in_room∈{leader,worker}, allow_from(白名单), state }
房间时间线        = 一条 Conversation(target_type="group")   ← 复用现有表，新 target_type
```
扩展（小迁移）— 解决 I2 作者归属：
```
ConversationMessage += sender_id (int, nullable)
                    += sender_label (str, nullable)   ← 仅群时间线用
```
锚点：`conversation.py:29-45` 加两列；现有 `target_type` 机制（`:17`）天然支持新值 `"group"`，**无需改 Conversation 表结构**。

> 迁移注意：`sender_*` 必须 nullable，旧消息全为 NULL，不影响 1:1 会话。

### 2.2 投影（复用 I4 多订阅者）

- 锚点：`stream_registry.py:381` `subscribers: set[Subscriber]`、`:391` `subscribe()`。
- 房间视图**同时订阅** N 个成员 `ActiveStreamTask` 的 buffer，**过滤后**只把"状态变化 + 已交结论"转发到房间时间线。
- 不改底层：每个员工仍是"一会话一流"（I4 不变），房间只是上层汇聚显示。
- 新增房间 SSE 端点（参考现有会话 SSE 订阅路径）。

### Phase 2 验收
- 房间时间线只出现"结论 / 状态变化"，不出现员工逐 token 全文。
- 多成员状态在一条时间线上正确归属到 `sender_label`。

## Phase 3 · @提及 + 白名单 + 凭证隔离 + 监督

薄路由层，复用现成 1:1 派发。设计文档 §6.4–6.5。

- **@派发**：群消息默认不触发；@某成员 → 把该消息作为 user 消息 **append 到目标成员私有会话 + `registry.start`**——与 `chat_service` 的 1:1 路径完全一致（`stream_registry.py:717` `start`）。零新机制。
- **白名单** `allow_from`：决定谁能 @ 谁，承载权限分级。省掉"LLM 选谁发言"。
- **凭证隔离**：员工不持真密钥，走内部中转带凭证 + 临时通行证。锚点：`llm/factory.py` 调用路径 + FastAPI 中介。
- **监督/心跳**：组长定时查进度、回收闲置成员（借 HiClaw heartbeat/idle）。

## 建议的交付顺序

1. **Phase 0**（1–2 天）：压测，确认路线 A 成立。
2. **Phase 1**（核心，可独立上线）：完成驱动调度器 + 多依赖。**此步交付后，现有串行编排即真正可用**，无需等房间。
3. **Phase 2**：房间模型 + 投影（"看得见"）。
4. **Phase 3**：@提及 / 白名单 / 凭证隔离 / 监督。

> 与既有治理一脉相承：先打牢单链路的缓存/验证/评估，再上群聊，否则群聊放大的是问题而非能力。
