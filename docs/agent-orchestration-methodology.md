# Agent 编排方法论：协调者中心 · 异步后台 · 经验闭环

> 一套与具体产品/模型无关、可复用的多 Agent 系统设计方法论。
> 抽象自一次实际重构，剥离了所有业务细节，只保留可迁移的架构模式。

## 术语

- **协调者 Agent（Coordinator）**：系统的唯一对话入口。接收用户需求、拆解、组队、派活、整合、交付。
- **工作 Agent（Worker）**：幕后执行单元，被协调者派活，自主完成子任务，不直接面对用户。
- **专才（Specialist）**：一类持久化、会成长的工作 Agent，持有自己的技能/记忆/经验画像。
- **共享工作区（Shared Workspace）**：协调者持有的单一产物目录，全队读写、互相可见。
- **私有记忆（Private Memory）**：每个专才私有的技能/记忆载体，是"成长"的家。

## 1. 核心心智：协调者唯一入口，工作者幕后

```
用户 ──对话──▶ 协调者 Agent（唯一对话面）
                   │
                   ├─ 判断复杂度：简单活自己干；复杂活 → 组队
                   ├─ 组队 → 派活（异步后台）
                   ├─ 回流 → 再入整合 → 交付
                   ▼
            共享工作区（全队协作、产物互见）
        工作 Agent A / B / C 并行后台跑（各带私有记忆入场）
```

**三条贯穿原则**：

1. **唯一对话面**——只有协调者与用户对话；工作 Agent 永不直接对话，只被派活、被查看。
2. **共享桌 + 私有脑**——产物落单一共享工作区；技能/记忆每个专才私有。
3. **涌现式成长**——专才名册从真实任务里"长出来"，不预定义、不靠人工维护，复用优先于新建。

**为什么这样分层**：把"对话/决策/整合"的复杂度集中在协调者一处，工作者只需专注"把一个自包含的活做完"。
用户心智简单（永远只跟一个入口聊），系统复杂度也收敛（HITL、上下文管理、交付都只在协调者层处理）。

## 2. 动态组队 + 涌现式持久名册

### 2.1 组队是核心交互

复杂需求不是交给一个万能 Agent 硬扛，而是协调者**按需拆解角色**、为每个角色绑定一个工作 Agent：

```
用户："帮我做一件复杂的事"
协调者：判断需要哪些角色 → 每个角色「复用优先于新建」
          ├─ 有匹配的老专才 → 复用（带经验加成）
          └─ 没有 → 现造一个 → 干完即持久化进名册
```

### 2.2 名册生命周期：涌现式持久个体

- **涌现**：组队现造的角色，干完活后**持久化**为专才，进入名册。
- **复用优先于新建**：组队时先按"能力画像"匹配老专才，匹配上就复用，匹配不上才新建。
- **成长落在个体**：专才"越用越强"，可被单独查看其成长轨迹。
- **防膨胀**：定期复盘（见 §3.3）退休长期闲置、合并近重复——避免名册无限膨胀。✅ 已由**生命周期 curator** 落地（`learning/curator.py`，搭 librarian 后台）：**技能**闲置老化 active→stale(30d)→archived(90d)（绝不删、可恢复、pinned 豁免，archived 逻辑隐藏不进路由）+ 近重复技能候选合并；**专才**侧保守——闲置 90 天只产**归档建议**、绝不自动归档（员工归档牵动路由，留用户决断）。详见 [learning-loop §7.6](learning-loop-self-evolution.md)。

### 2.3 用户可显式引导路由

除了协调者自动路由，提供一个轻量的**显式引导**手势（如 `@某专才`）：它是**给协调者的路由提示**
（"这活让谁接"），叠在自动路由之上，**不等于绕过协调者直接对话**。候选只来自名册已有专才。

> 关键区分：自动路由是默认，显式引导是叠加；二者都经协调者，工作者始终不直接对话。

## 3. 经验闭环（让专才越用越厚）

### 3.1 两种经验形态，不同成本、不同闸门

| 形态 | 是什么 | 写入成本 | 触发 |
|------|--------|---------|------|
| **情景记忆**（episodic） | "这类活上次怎么干、产物在哪、成没成" | 近乎免费（只记日志，不调模型） | **每个子任务完成，自动** |
| **可复用技能**（procedural） | "这类活的标准打法/模板/SOP" | 贵（需 critic 提炼） | **强信号才触发** |
| **零散教训**（memory） | "偏好这样、那个坑别再踩" | 贵 | **强信号才触发** |

### 3.2 四个环节

```
①捕获(自动·免费) ─▶ ②提炼(信号·后台critic) ─▶ ③复盘(定期·后台librarian) ─▶ ④回喂(派活时)
```

- **①捕获**：子任务一结束，**自动**追加一条结构化流水（任务摘要、用了哪些工具/技能、成败、产物路径、
  耗时/成本等）。**不调模型**，近乎零成本。捕获字段应覆盖所有"信号"的判定来源。
- **②提炼**：**只有强信号才跑**——一个**独立的轻量 critic 在后台异步**读相关流水 + 信号，提炼成技能或教训。
  不占用户等待、不污染协调者主上下文。技能不止于"新造候选"：员工干活中发现已加载技能错/缺/过时，可用 `update_skill` **就地修订老技能**（只改自己的私有副本、按员工隔离，2026-06-25 路2；技能在用中自改进，见 [learning-loop §7.5](learning-loop-self-evolution.md)）。
- **③复盘**：后台 librarian 周期性（或记忆超阈值时）合并重复、删过时、更新能力画像；第 4 步 **curator** 做生命周期管理（技能闲置老化隐藏 + 近重复候选合并 + 员工归档建议，保守可逆，见 §2.2）。
- **④回喂**：见 §3.4。

### 3.3 "什么算信号"（信号闸门是质量的关键）

只有强信号才触发昂贵的提炼，其余只进便宜的情景流水：

| 信号 | 含义 | 提炼成 |
|------|------|--------|
| **用户纠正** | 用户指出"不对，应该…" | 教训（软）——最强信号 |
| **失败后成功** | 炸了→重试→成了，这个 diff 就是教训 | 教训："这么做会炸，那么做才行" |
| **重复模式** | 同一打法跨任务出现 N 次，被验证 | 技能（硬）——验证过才晋升 |
| **显式记住** | 用户/协调者说"记住这个" | 技能或教训 |
| **验收返工** | 协调者整合时判定某子任务要返工 | 教训：返工原因 |

**核心防坑：单次成功不直接晋升技能**（防止把侥幸当真理）。单次信号只进"软知识"（教训），
只有**重复出现 / 被验证**才晋升为"硬知识"（技能）。这是信号闸门的真正价值。

### 3.4 统一概念：能力画像（一物三用）

每个专才自动维护一份简短的能力画像（擅长什么、干过哪类活、踩过哪些坑），由复盘环节更新。一处产出，三处消费：

1. **路由**：协调者组队时读画像，决定派给谁/是否新建——**路由本质就是检索**。
2. **回喂**：派中的专才，技能自动加载常驻 + 一个"搜记忆"工具按需深查。
3. **查看**：对外只读展示的头条 = 画像 + 底下的技能/记忆/历史。

### 3.5 学习闭环的取舍原则

- **不在用户等待路径上反思**——critic/librarian 全后台异步。
- **不让单次轨迹造硬技能**——防 fluke。
- **自清理防腐化**——复盘合并/退休，记忆库与名册都要能瘦身。
- **先摘要后向量**——能用"画像摘要 + 关键词/工具检索"解决就别急着上 embedding 语义库（YAGNI）。

## 4. 异步后台执行 + 再入整合

### 4.1 极简执行引擎

```
协调者接需求 → 产出一个 Plan
   Plan = 一组 Task，每个 Task 可选 depends_on（最小依赖，不是重型 DAG 编排）
调度器：依赖满足的 Task 就发车；受准入 + 并发上限约束（保护算力/配额）
Task 状态机：queued → running → done/failed/interrupted（持久化，可跨重启）
```

> 依赖是多角色协作绕不开的（B 依赖 A 的产出），但**只做最小 `depends_on`**，不引入重型编排框架。

### 4.2 ★ 再入整合（异步系统的核心难点）

**同步子代理**（派完在同一轮等结果）天然在本轮整合，无需"再入"。但**真异步后台**里，协调者那一轮
早已返回，子任务后台跑完后协调者必须"醒来"整合——这是异步系统 bug 最容易聚集的地方。

**方案：事件驱动唤醒 + 批量节流**

```
子任务完成 → 写一条「完成事件」(结论摘要 + 产物路径 + 状态)
                  │
       协调者的协调器在监听
                  │
       一批/关键任务完成 → 触发一个「整合轮」(系统事件触发，而非用户消息触发)
                  │
       协调者读回流结果 → 整合 → 交付用户
```

**关键能力**：协调者会话能被**外部事件**（而非只有用户消息）触发新一轮。
**防风暴**：整合轮**串行 + 节流**，攒一批再醒，不每个子任务都打断用户。
**可调旋钮**：逐个回流（碎但实时）vs 攒齐回流（整但慢）。

### 4.3 两条经 Claude Code 验证的原则

Claude Code 处理"后台任务完成 → 主 agent 唤醒整合"用的正是同一套（轻量通知 + 主代理按需拉输出 +
通知排队、agent 自决何时处理）。从中固化两条原则，显著降低复杂度与上下文膨胀：

1. **通知轻量化**：完成事件**只带**摘要 + 产物路径 + 状态，**绝不塞完整输出**；协调者被唤醒后
   **按需**去拉详情。（对标 Claude Code：notification 只带"完成了 + id/路径"，agent 再自拉。）
2. **编排层与主上下文分离**：子任务的**全过程**（逐字独白、中间工具调用）**留在进度面板/编排层，
   不回吐协调者主上下文**；再入整合时**只读精炼结论**。这防止主上下文被一堆子任务过程淹没。
   （对标 Claude Code 的 Workflow：中间结果留编排层，主循环只收最终报告。）

### 4.4 工作者无澄清：自包含派单

工作 Agent 拿到**自包含的派单**，自主跑到底，**绝不回头问**。需要澄清时一律由协调者层处理：

```
两处澄清，都在协调者层（工作者全程不阻塞）：
① 派活前  需求本身模糊 → 协调者先问用户 → 问清再派
② 回流后  子任务信息不足 → 把「做了X假设」或「缺Y信息」写进【结果】带回
            → 协调者再入整合时自行决定：用假设继续 / 回头问用户 / 补料重派
```

**收益**：异步引擎**不接**工作者的人机交互中断；再入整合只处理"完成/失败"两种终态，不处理
"中途被打断要人答"，bug 面大幅收窄。所有人机交互的复杂度都收敛在协调者一处。

工作者派单原则：**自包含 + 自主决策 + 缺啥写进结果带回，绝不阻塞等人**。

## 5. 共享工作区 + 私有记忆

```
共享工作区（产物）：单一协调者级目录，全队读写、互相可见
   <workspace>/
       ├── task-<id>/ …    ← 各子任务自己的子目录（靠命名约定防撞名）
       └── …
私有记忆（每个专才私有，成长的家）：
   <brain>/<specialist-id>/{ 流水, 技能, 记忆, 能力画像 }
```

- **产物共享、互见**：全队在一个工作区协作，上游产出下游立即可读——比"每个 Agent 各自目录再来回传"简单得多。
- **记忆私有、隔离**：专才之间读不到彼此的私有记忆，成长归个体；好打法要全队共享时，靠复盘半自动提升，
  不自动扩散。
- **并发写**：靠子目录/命名约定避免撞名，第一版不做文件锁（YAGNI）。

## 6. 适用与不适用

**适合这套方法论的场景**：
- 需求复杂度跨度大（有的一句话能答、有的要拆成多角色协作）。
- 希望"用户心智简单、系统能力可成长"——单一入口对外，能力库在内部沉淀。
- 子任务之间相对独立、可并行、可异步（长任务尤其受益）。

**不适合 / 需谨慎**：
- 子任务高频需要人在环里逐步确认——本方法论刻意把工作者设计成"无澄清"，这类场景要么前移到协调者层澄清，
  要么本方法论不适用。
- 需要工作者之间频繁实时双向通信、共享细粒度中间状态——那更接近"多全功能会话互通"的重型模型，
  本方法论的"工作者只回流结论"会成为限制。
- 强一致/事务性协作（多 Agent 改同一份强一致数据）——共享工作区的"命名约定防撞名"不够，需要额外的锁/事务层。
