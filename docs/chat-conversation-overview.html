③ 三条容易出错的特殊流程

HITL 审批

流式中遇到澄清/危险删除/文档计划工具 → 后端 interrupt → transport 收到 status:interrupted → 总线通知 session → 封存这条 msg_A、弹审批卡。
用户点通过 → approveHitl(POST /approve) → 后端封存 msg_A + 新建 msg_B + resume → 前端 onHitlApproved：打 approved_at → dispatch HITL_APPROVED → 登记 sealed → resume。

Resume 续流

两种触发：① 审批后续跑；② 重进/切回一个"后端还在 streaming"的会话（shouldAttemptResume 判定）。 都走 reconnectToStream → GET /resume，复用同一套解析。
关键坑：resume 会把"触发中断的旧消息"重放，要靠 sealedToolCallIds 跳过，否则与 msg_A 重复。

Hydrate 水合

切回会话 / 流结束后，把 DB 的 initialMessages 同步进 composer。 由 decideHydration 决定：none（不动）/ replace（整表换）/ patch（同轮只补 id/状态，保留 SSE 累积的 parts，防闪屏）。 流式进行中（status=streaming）直接早返回，绝不 hydrate，否则会覆盖正在写的内容。

B. 会话状态机重构（P1-2 · 核心）

问题：useConversationSession 用 6 个 useRef + 多个 effect 拼出一个"看不见的状态机"，时序敏感，是偶发 bug 的温床。

修复：重构成 纯 reducer + 纯决策函数 + 薄 hook（session/ 目录，全部带单测）。行为逐字保持，公共 API 不变。经 7 次评审 + 人工冒烟通过。

过程中抓到一个真回归（已修）：重构时把簿记从 ref 搬进 reducer 又放进了 effect 依赖 → effect 内 dispatch 触发自重跑，cleanup 把刚排好的 requestAnimationFrame resume 取消了 → "切回 streaming 会话不恢复"。
修复：引入 machineRef 非响应式读取，依赖只列外部输入（复刻旧 ref 语义）。— 这正是只有人工冒烟才能发现、现已写成自动化测试的那类时序 bug。

C. 审批后"工具块/文本重复"（你最在意的偶发 bug）

根因（真实 SSE 抓包确证）：审批后 /resume 时，后端 deepagents 的 HumanInTheLoopMiddleware 会把"触发中断的那条 AIMessage(工具调用) + ToolMessage" 作为头部事件重放一遍；它的 toolCallId 已经封存在中断消息 msg_A 里，而续跑内容写进新建的 msg_B，前端把 msg_A+msg_B 合并显示 → 同一工具调用出现两份。原来的去重只在状态对齐时生效 → 所以"偶发、补丁不确定修没修好"。

修复 A（源头）
parser 新增 sealedToolCallIds，resume 时跳过这些已封存 id 的重放（transport 经 setResumeSealedToolCallIds 播种，onHitlApproved 登记 HITL toolCallId）。
修复 B（兜底）
parts-dedupe 增 dedupeToolPartsByToolCallId：合并气泡内同 toolCallId 工具块只留一份（优先有 output 的），不依赖类型/状态对齐。

✅ 人工冒烟确认：审批后不再重复。
