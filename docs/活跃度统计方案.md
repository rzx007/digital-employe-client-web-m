## 一、背景与约束

要统计两个指标：

1. **用户活跃度** —— DAU / WAU / MAU，精确到具体用户。
2. **技能活跃度** —— 每个技能被多少用户、用了多少次，精确到具体用户。

已确认的关键约束（决定了方案走向）：

| 约束 | 影响 |
|---|---|
| **服务端只有「技能市场」是活的，其它功能（含任务执行记录 `task_execution_record`）均已废弃** | 技能活跃度**不能**复用服务端执行记录，必须**全靠客户端埋点** |
| 数据要**精确到具体用户** | 每条事件都要带 `user_id` |
| 用户活跃度**只要 DAU/WAU/MAU，不要在线时长** | **不做心跳**，省去主进程定时器，登录/启动事件即可判活 |
| **后台需要可视化** | 服务端需出统计查询接口 + 一个可视化页面（位置待定，见 §5） |

## 二、现状摸底结论

### 客户端 `digital-employee-client`

- HTTP 统一封装：`apps/web/src/lib/request.ts`（ofetch），已自动注入 `token` 与 `X-Workspace-Id` —— 天然的全局拦截点。
- 用户唯一标识：`useAuthStore().user.id`；登录 / 登出 / 会话恢复都在 `apps/web/src/stores/auth-store.ts`。
- 技能模块：`apps/web/src/components/skills/` + `apps/web/src/api/skill.ts`，技能含 `id` / `skillName` / `displayNameZh`。
- **目前无任何埋点 / telemetry 模块**，从零新增。

### 服务端 `actus-digital-employee`

- 技术栈：FastAPI + **Tortoise ORM** + **Aerich 迁移**（注意：不是 SQLAlchemy/Alembic）。
- **无 User 表**：用户身份来自请求头 `userid` 或 JWT，解析逻辑在 `src/core/request_utils.py` 的 `get_authenticated_user_id()`。→ 服务端天然能拿到可信 `user_id`。
- 现有 `audit_log`、`task_execution_record` 等属于**已废弃功能**，本方案**不依赖**它们，新建独立的干净事件表。
- 迁移目录：`migrations/models/`，配置 `aerich_config.py`。

## 三、核心设计思路

技能活跃度和用户活跃度，**统一收敛到一张客户端事件表**：

- 客户端在关键行为点埋点 → 攒批上报 → 服务端落库到一张 `actus_client_activity_event` 表。
- **用户活跃度**：当天出现任意带 `user_id` 的事件即视为活跃，按天去重 `user_id` 得 DAU，再按周/月聚合得 WAU/MAU。
- **技能活跃度**：筛 `event_type` 为技能类的事件，按 `skill_id` group by。

> 单表 + `event_type` 区分，比建多张专用表灵活，统计全靠 SQL group by。**初期不做日聚合表**，数据量大了再加 `*_daily` 加速。

## 四、服务端改动（actus-digital-employee）

新建模块 `src/api/v1/analytics/`（放在技能市场所在的活模块附近）。

### 4.1 事件表 —— `src/models/analytics.py`

```
actus_client_activity_event
  id            BigInt PK
  event_type    varchar idx   # login / app_open / skill_view
                              # / skill_install / skill_uninstall / skill_edit / skill_invoke
  user_id       varchar idx   # 服务端从 token 解析，不信客户端传的（防伪造）
  tenant_id     varchar idx
  workspace_id  varchar null
  skill_id      BigInt null idx   # 技能类事件才有
  skill_name    varchar null
  client_ver    varchar null      # 客户端版本，便于分版本看活跃
  platform      varchar null      # win / mac / linux
  occurred_at   datetime idx      # 事件发生时间（客户端给，用于补传 / 时区）
  created_at    datetime idx      # 入库时间
  extra         JSON null         # 预留扩展字段
```

### 4.2 上报接口 —— `src/api/v1/analytics/router.py`

- `POST /api/v1/analytics/events`
  - 接收**批量** events 数组（客户端攒批上报，减少请求数）。
  - `user_id` / `tenant_id` **以服务端从 token 解析为准**（`get_authenticated_user_id`），客户端传值仅作兜底，防伪造。

### 4.3 统计查询接口（供后台可视化）

- `GET /api/v1/analytics/users/active?granularity=day|week|month&from=&to=`
  → DAU / WAU / MAU 时间序列（按天去重 `user_id`，再按周 / 月聚合）。
- `GET /api/v1/analytics/skills/ranking?from=&to=&metric=invoke|install|view`
  → 技能活跃榜：每个技能的 **调用次数 / 去重用户数 / 安装数**。
- （可选）`GET /api/v1/analytics/users/{user_id}/skills`
  → 单用户用了哪些技能（满足「精确到具体用户」）。

### 4.4 迁移

```bash
aerich migrate    # 生成迁移文件
aerich upgrade    # 执行（注意是 Aerich，不是 Alembic）
```

## 五、客户端改动（digital-employee-client）

### 5.1 埋点模块 —— 新建 `apps/web/src/lib/telemetry.ts`

- 内存队列 + 攒批 flush（满 20 条或每 30s）+ `before-quit` 兜底 flush。
- 每条事件自动带：`user.id` / `workspaceId` / `client_ver` / `platform` / `occurred_at`。
- 复用 `src/lib/request.ts` 发往 `/api/v1/analytics/events`。
- fire-and-forget，失败重试，离线落本地缓存，**绝不阻塞 UI**。

### 5.2 埋点挂载点（均为现成位置）

| 事件 | 挂载文件 |
|---|---|
| `login`（DAU 主依据） | `apps/web/src/stores/auth-store.ts` 的 `login()` 成功分支 |
| `app_open`（会话恢复也算当天活跃） | `apps/web/electron/core/bootstrap.ts` / `restoreSession()` |
| `skill_view` | `apps/web/src/components/skills/skills-list-view.tsx` 的 `onSelectSkill` |
| `skill_install` / `skill_uninstall` | `skills-list-view.tsx` 的 `tryInstallRemote()` 等 |
| `skill_edit` | `apps/web/src/components/skills/skill-detail-view.tsx` 保存处 |
| `skill_invoke`（对话中真正用到技能，如适用） | 聊天发送处（**待确认是否有明确触发点**） |

> 因为不要在线时长，**任何带 `user_id` 的事件当天出现一次即算活跃**，`login` + `app_open` 已足够判定 DAU，无需心跳。
