## 🎯 最高杠杆

### #1 计划卡片 inline-edit（改了再确认）
- **现状**：编排计划卡片只有「确认执行 / 取消」，要么照单全收，要么推倒重来。
- **痛点**：用户发现「任务3 派错人 / prompt 少一句」，只能取消并重新长篇描述需求、等总管重建。
- **做法**：卡片每条子任务可**改 prompt / 换员工 / 删除**，确认时提交编辑后版本。
- **涉及**：前端 `apps/web/.../message-blocks/plan-generated-card.tsx`（已列任务，缺可编辑态）；后端 `orchestrator/tools/tasks.py::update_task`（agent 侧已有）——直连前端可能需补一个 REST 编辑端点 + 校验（复用 `task_validation` 的 DAG 自检）。
- **注意**：编辑后须重跑 `validate_orchestration_tasks`（成环/越界）再落库。

### #2 进化「看得见」——成长在对话里主动冒泡
> **v1 已完成**（commit `33b813a7`）：联系人卡片头像「✨N」角标 = 待确认技能候选数（`employee_detail_dict.skill_candidate_count` → `EmployeeRead` → 前端 `AIEmployee.skillCandidateCount` → contact-item 角标；采纳/忽略后失效 contacts 查询即时增减）。**v2 待做**：总管在合适时机主动提一句「X 这套打法成功 N 次了，要不要存成技能？」。
- **现状**：技能候选、画像增长都埋在成长面板，需用户主动点进去；学习闭环后台默默跑，用户感知不到员工变强。
- **痛点**：「自主进化」是最大卖点却对用户隐形。
- **做法**：
  - `promote_skills` 写出新候选时推一个 workspace 事件 → 员工卡片加「✨ 新技能待确认」角标。
  - 合适时机总管主动提一句「X 助手这套打法最近成功 N 次，要不要存成技能？」（候选/画像数据已就绪，只差触达 + 触发时机）。
- **涉及**：`learning/librarian.py::promote_skills`（写候选后 `WorkspaceEventBus.push`）；前端联系人/员工卡片角标 + `growth-brain-section.tsx`；总管提示词/再入处的「成长播报」时机（避免打断主任务）。
- **注意**：触达要克制——别每次复盘都打扰；角标 + 偶发一句即可。

## 🟠 显著改善

### #3 交付物「再改改」一键返修
- **现状**：员工交付后，改动得重新打字描述需求。
- **做法**：产物/交付卡片加「让TA改改」入口，写一句意见 → 走 `redispatch_task` 在原员工会话返修。
- **涉及**：前端产物面板 / 交付卡片；后端 `orchestrator/rework.py::redispatch_task_in_session`（机制已有）——前端触发可能走「向总管发一条带 task 引用的消息」或补一个返修端点。
- **注意**：返工有上限 2 次 + 前置 gate，沿用现有约束。

### #4 信任档位 / 按类免确认
- **现状**：P1-A 仅「单任务+只读+无cron+无破坏词」自动执行，其余每次确认。
- **痛点**：高频重复工作流（如每日「查热搜→生成周报」）每次都要点确认。
- **做法**：用户可设「记住，这类以后直接执行」或工作区级信任档位（如「≤N 任务非破坏性自动跑」）。
- **涉及**：`orchestrator/confirmation_policy.py::compute_requires_confirmation`（接入档位）；会话/工作区 flags（参考 `destructive_hitl.py` 的 `session_flags` 模式）；前端设置入口。
- **注意**：被派员工 HITL-off，放宽自动执行有安全权衡——保持破坏性词强制确认，档位只放宽「非破坏性」范围。

### #5 等待期「现场感」——员工在干什么
- **现状**：后台任务 running 时用户只看到「⏳ 进行中」+ 完成摘要；中间过程按设计留编排层。
- **痛点**：复杂任务跑几十秒~几分钟，盯着「进行中」会焦虑、疑似卡死。
- **做法**：「员工任务」面板给每个 running 任务显示一行轻量实时状态（当前调什么工具/写什么文件）；不回吐总管主上下文。
- **涉及**：`WorkspaceEventBus`（task 过程事件，部分已有 task_started/completed）；前端 `task-progress-bar.tsx` / 员工任务面板；`use-workspace-events.ts`。
- **注意**：只做「看得见在动」的轻量展示，不破坏「编排层与主上下文分离」原则。

## 🟡 锦上添花 / 看准再做

### #6 「团队能做什么」首页 / 新手引导
- **痛点**：新用户面对空对话框，不知团队能干嘛、有哪些员工/技能。
- **做法**：空状态给「团队名片」——现有员工+技能+几个可点示例指令。
- **涉及**：前端聊天空状态；`list_workspace_employees` / `list_workspace_skills` 数据。

### #7 失败/跳过的「为什么 + 一键恢复」
- **现状**：上游失败 → 下游级联 `skipped`，用户拿到大半跳过的计划。
- **做法**：失败/跳过节点显示原因 + 「重试 / 换人 / 改需求」一键入口。
- **涉及**：`dependency_scheduler.py`（skip reason 已写入 `run_result`）；前端 DAG / 任务面板。

### #8 @点名员工路由
- **现状**：方法论 §2.3 设想「@某专才」作为给总管的路由提示，**需先验证是否已实现**。
- **做法**：用户 @某员工暗示「这活让TA接」，仍经总管编排（不绕过）。
- **涉及**：前端输入框 @ 补全；总管提示词消费路由提示。
- **注意**：先确认现状再决定做不做。

## 横切原则（实现时守住）
- 不破坏「唯一对话面」「编排层与主上下文分离」「确认门保守、被派员工 HITL-off 的安全边界」。
- 触达类（#2 冒泡、#5 现场感）要**克制**，别把通知变骚扰。
- 凡改行为/提示词，沿用本仓库 TDD + 提交节奏；改确认/放行逻辑务必跑全套回归。
