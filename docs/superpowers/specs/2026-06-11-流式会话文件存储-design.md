# 流式会话文件存储设计

- 日期：2026-06-11
- 状态：已评审（设计阶段通过，待实现计划）
- 方案：A（自定义文件 checkpointer，复用 LangGraph `InMemorySaver` 公共 API + per-thread 原子落盘）

## 1. 背景与动机

当前流式会话涉及两套 SQLite 存储：

1. **`checkpoints.db`** —— LangGraph `AsyncSqliteSaver`，存 Agent 执行状态/断点续传快照。每个 super-step 写大 checkpoint（observed 110KB+），且是**单条共享 `aiosqlite` 连接**串行落库。群聊多路并发流时，这条单连接成为串行瓶颈，是"群聊组长流第一步卡死"的疑点根因。
2. **`app.db` 的 `conversation_messages` 表** —— 业务库，存 `stream_state` / `stream_cursor` / `content` / `message_parts` 等。已用单线程写队列（`_DB_WRITE_EXECUTOR`）+ `RLock` + WAL 兜并发。

用户诉求：把流式会话存储改为**文件存储**，因为单 SQLite 连接在多路并发流下会串行/卡死（用户表述为"sqlite 不支持多线程并发、不支持连接池"）。

> 说明：SQLite 在 WAL 下本支持多读单写，代码也堆了一圈 workaround。真正痛点是 **checkpointer 那条共享连接的串行化**。文件存储用 **per-thread 一个文件**做隔离，从根上消除跨流锁竞争。

部署形态：本地桌面 Electron + 本地 Python 后端，单用户，并发流上限 `AGENT_MAX_INFLIGHT=4`（群聊场景）。并发规模小，per-file 隔离方案完全够用。

## 2. 范围与边界

**目标**：把流式会话的两套存储都改为文件存储。

**业务侧边界 —— 只搬瞬时进度，不动会话历史**：

| 数据 | 去向 | 理由 |
|------|------|------|
| `stream_state` / `stream_cursor` / 流到一半的 `content` | → 文件（per-message sidecar） | 流式过程中高频写，是并发争锁来源 |
| 终态 `content` / `message_parts` / `usage` | 仍留 `app.db`（`conversation_messages`） | 历史详情/群时间线/usage 估算等 14 个读点全部不动 |
| 心跳 `last_heartbeat_at` | 仍留 `app.db`（`TaskExecutionLog`，非本表） | 30s 低频，写的是另一张表，不在本次范围 |

业务读路径改动**集中在 2 个点**（消息列表/详情序列化 overlay + `get_stream_status`），而非全部 14 个读点——因为终态落库后进度文件即删，历史读全程读 DB、不受影响。

**非目标（YAGNI）**：
- 不重写会话历史存储（`conversation_messages` 行本身保留）。
- 不改 `TaskExecutionLog` 心跳。
- 不引入跨进程文件锁框架（单进程后端，per-thread 锁足够）。
- 不做 checkpoint 时间旅行（time-travel）；只需 resume 最近 checkpoint。

## 3. 崩溃恢复要求

应用崩溃/进程被杀后重启，流式会话需能**从中间点继续跑**（与当前 `AsyncSqliteSaver` 行为一致）。因此：

- checkpointer journal 写入需 `append + fsync`，保证最近 checkpoint 落盘。
- 进度 sidecar 写入需 `临时文件 + fsync + os.replace` 原子落盘。

## 4. 环境与版本

- `langgraph==1.2.2`，`langgraph-checkpoint==4.1.1`，`langgraph-checkpoint-sqlite==3.0.3`。
- 适配只依赖 langgraph-checkpoint **公共 API**：`BaseCheckpointSaver` 接口、`InMemorySaver`/`MemorySaver` 的 `put`/`aput`/`put_writes(config, writes, task_id, task_path)`/`aput_writes`/`get_tuple`/`aget_tuple`/`list`/`alist`/`delete_thread`/`adelete_thread`、`CheckpointTuple`（含 `.config` `.checkpoint` `.metadata` `.parent_config` `.pending_writes`）。不触碰内部 `.storage`/`.writes`/`.blobs` 字段，降低版本升级碎裂风险。

## 5. 目录布局

复用 `settings.sqlite_path` 同级目录（`resolve_sqlite_path(...).parent`），新增两个子目录：

```
{data_dir}/
  app.db                      # 业务库（不动；终态历史记录仍在此）
  checkpoints/                # 替代 checkpoints.db
    {thread_id}.jsonl         # thread_id = conversation_id；每会话一个 journal
  stream_progress/            # 业务侧瞬时进度
    {message_id}.json         # 流到一半的 state/cursor/content
```

每会话 / 每消息一个文件 = 天然隔离，并发流各写各的文件，零跨流锁竞争。

## 6. Part A：文件 checkpointer（`FileCheckpointSaver`）

`FileCheckpointSaver(BaseCheckpointSaver)`，采用 **journal + 重放** 模式，全程只用公共 API。

### 6.1 数据结构

- 每 thread（= conversation_id）一个 `{checkpoints_dir}/{thread_id}.jsonl` journal 文件。
- 每行一条操作记录（JSON）：
  - `{"op":"put", "config":..., "checkpoint": <serde bytes b64>, "metadata": <serde b64>, "new_versions":..., "ts":...}`
  - `{"op":"writes", "config":..., "task_id":..., "task_path":..., "writes":[[channel, <serde b64>], ...]}`
- 内存侧：每 thread 一个懒加载的 `InMemorySaver` 委托实例（`_delegates: dict[thread_id, InMemorySaver]`）作为读缓存。

序列化用 `self.serde`（`BaseCheckpointSaver` 自带的 `JsonPlusSerializer`），把 checkpoint / 写入值转成 `(type, bytes)`，bytes 经 base64 入 JSON 行。

### 6.2 写路径（`aput` / `aput_writes`）

1. 取 per-thread `asyncio.Lock`。
2. 用 `self.serde.dumps_typed(...)` 序列化 checkpoint/metadata/写入值。
3. 把一行 JSON `append` 到 journal 文件，`flush` + `os.fsync`（阻塞 IO 丢专用线程执行器，不堵事件循环）。
4. 同步更新内存委托实例（`delegate.put(...)` / `delegate.put_writes(...)`），保证后续读命中缓存。
5. 返回 `aput` 应返回的 `config`（带新 `checkpoint_id`）。

> 追加写天然不破坏已有行，崩溃最多丢正在写的那一行（fsync 前），上一个完整 checkpoint 仍可 resume。

### 6.3 读路径（`aget_tuple` / `alist`）

- 懒加载：首次访问某 thread 时，读 journal、逐行用委托的 `put` / `put_writes` 重放，重建 `InMemorySaver` 委托；之后走内存缓存。
- 读操作直接转发给委托实例（`delegate.aget_tuple(...)` / `delegate.alist(...)`）。
- journal 文件不存在 → 该 thread 无 checkpoint，返回 `None` / 空。

### 6.4 删除（`adelete_thread`）

- 丢弃内存委托缓存 + `unlink` journal 文件（缺失则忽略）。
- 终态流程照常调用（`delete_conversation_checkpoint` → `adelete_thread`），清理瞬态。

### 6.5 压实（compaction）

- journal 行数超阈值（如 200 行）时触发：用 `alist` 拿回该 thread 全部 `CheckpointTuple`（公共 API），把每个 tuple 反构成最小的 `put` + `put_writes` 操作序列，原子重写（temp + fsync + replace）journal。
- 正常会话终态即 `adelete_thread`，journal 短命，基本触发不到压实；压实仅为长会话兜底，防 journal 无界增长。

### 6.6 同步接口

`BaseCheckpointSaver` 要求 sync 方法（`put`/`get_tuple`/`list`/`put_writes`/`delete_thread`）也实现。沿用同一 journal 格式，sync 路径直接做阻塞文件 IO + fsync。async 路径把 sync 实现丢线程执行器。

### 6.7 接线点

- `src/service/agent/checkpointer.py`：
  - `get_checkpointer()` 按 `settings.checkpointer_backend` 返回 `FileCheckpointSaver`（默认）或 `AsyncSqliteSaver`（回滚）。
  - `init_checkpointer(...)` 不再需要 `aiosqlite` 连接，改为接收 checkpoints 目录路径并实例化 `FileCheckpointSaver`。
  - `delete_conversation_checkpoint` 不变（仍调 `adelete_thread`）。
  - `init_memory_checkpointer()`（`MemorySaver`）保留给测试。
- `src/server.py`：启动不再 `aiosqlite.connect(checkpoints.db)` + 一串 PRAGMA；改为创建 checkpoints 目录并 `init_checkpointer(checkpoints_dir)`。

## 7. Part B：业务瞬时进度 sidecar

### 7.1 进度文件格式

`{stream_progress_dir}/{message_id}.json`：

```json
{
  "message_id": 123,
  "conversation_id": 45,
  "stream_state": "streaming",
  "stream_cursor": 1500,
  "content": "…流到一半的纯文本…",
  "updated_at": "2026-06-11 12:00:00"
}
```

### 7.2 写路径

- `_checkpoint_flush_sync`（每 `BUFFER_CHECKPOINT_LEN=500` 事件触发）改为：原子写 `{message_id}.json`（temp + fsync + `os.replace`），**不再写 DB**。高频写彻底离开 SQLite。
- 进度文件写入封装为独立模块（如 `src/service/stream_progress_store.py`），按 `settings.stream_progress_backend`（`file`|`sqlite`）选实现，留 DB 老路径回滚。

### 7.3 读 overlay

- 消息列表/详情序列化（`ConversationMessageRead` 相关组装处）：若某消息存在进度文件，用文件里的 `stream_state`/`stream_cursor`/`content` **覆盖**行上的值。
- `StreamRegistry.get_stream_status` 的 DB fallback 分支：改读进度文件（缺失则回退读行上旧列值，保证向后兼容）。

### 7.4 终态

- `_flush_terminal_sync`：仍一次性把最终 `content` / `message_parts` / `usage` / `state` 写 `app.db`（历史永久记录，逻辑不变），**随后删除进度 sidecar 文件**。此后 DB 为唯一真相，overlay 自动失效。

### 7.5 状态标记

- `_mark_stream_state_sync` 中对 `TaskExecutionLog` 的写保持走 DB（另一张业务表，低频）。
- 其中对 `conversation_messages` 的 `stream_state` / 占位 `content` 改为写进度 sidecar（如 `queued` 占位文案）。overlay 让前端读到一致视图。

## 8. 原子性 / 崩溃恢复 / 并发

- **原子写**：进度 sidecar 用 `临时文件 + fsync + os.replace`；checkpointer journal 用 `append + fsync`。
- **崩溃恢复**：重启后——
  - checkpointer journal 还在 → LangGraph 从最近 checkpoint resume 中间点；
  - 进度 sidecar 还在 → 消息列表/resume 显示已生成文本与 cursor。
  - 两者共同满足"中间点也要能续"。
- **并发模型**：
  - 跨会话：per-file 隔离，不同 conversation_id 永不碰同一文件 → 无跨流锁竞争（核心收益）。
  - 单会话内：LangGraph 本就串行 super-step；再加 per-thread `asyncio.Lock` 兜 put/delete 交叉。
  - `_DB_WRITE_EXECUTOR` 保留给剩余 DB 写（终态、`mark_state` 的 TaskExecutionLog 部分、心跳）；高频 checkpoint 写已移出，争用消失。
- **性能**：append+fsync 每 super-step 写量（~110KB）与原 SQLite 相当，但 per-file 消除跨流串行；桌面 SSD 下可接受。

## 9. 迁移 / 上线 / 回滚

- **无需数据迁移**。`checkpoints.db` 为瞬态库，应用重启本就 cancel 所有活动流，升级时无活流可丢；旧文件弃用即可（删与不删均无害）。
- **向后兼容靠"文件缺失即回退"**：升级前遗留的 `stream_state='streaming'/'interrupted'` 老消息无进度 sidecar → overlay 读不到文件时回退读行上旧列值（列保留未删）。新老消息无缝共存。
- **一处可接受损耗**：升级前正卡在 HITL `interrupted` 的会话，其 checkpoint 在旧 `checkpoints.db`、新 journal 无 → 该会话 resume 失败（需用户重发）。一次性、极少见，文档标注。
- **回滚开关**：
  - `settings.checkpointer_backend`：`file`（默认）| `sqlite`。`get_checkpointer()` 据此选实现，保留一版 SQLite 老路径。
  - `settings.stream_progress_backend`：`file`（默认）| `sqlite`。进度存储据此选实现。
  - 线上出问题可一键切回 SQLite。
- **测试环境不动**：`init_memory_checkpointer()`（`MemorySaver`）保留给 pytest。

## 10. 测试策略

- **`FileCheckpointSaver` 单测**：put/get_tuple 往返；put_writes → `pending_writes`；list；delete_thread；子图 `checkpoint_ns`；**重放**（新实例同目录读 journal 还原状态）；**压实等价**（压实前后 `alist` 结果一致）；跨 thread 并发 put；**原子性**（temp/replace 之间模拟崩溃 → 旧文件完好）。
- **契约测**：真实 LangGraph agent 图跑 interrupt→resume，断言文件 checkpointer 与 `AsyncSqliteSaver` 行为一致（golden 对比）。
- **Part B 单测**：sidecar 写/读/overlay/终态删除；`get_stream_status` 读文件；**文件缺失回退行**；序列化器 overlay 正确。
- **集成测**：模拟群聊 4 路并发流 → 断言无 `database is locked`、各自独立 resume；崩溃恢复（写 checkpoint → 杀进程 → 重启 → 中间点续跑）。
