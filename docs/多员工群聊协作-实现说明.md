## 一、做了什么（4 个阶段）

### Phase 1 · 完成驱动调度器（修复伪 DAG）— 核心价值，可独立交付
**问题**：旧 `start_immediate_tasks` 在任务**启动时**就递减后继依赖，"B 等 A 做完"从未真正发生。

**改动**：
- 新增 `apps/server/src/service/agent/orchestrator/dependency_scheduler.py`
  - `on_employee_task_completed(task_id, workspace_id)`：任务真正完成时，用 **DB 派生计数**（按 `TaskExecutionLog.run_status=="completed"` 判断前置是否齐活）解析可派的后继并派发。重启不丢状态、并发安全、幂等。
  - 支持 `depends_on` 为 **int / int[]**（多依赖汇合）。
  - 派后继时把前置产物**引用**（路径/摘要，非全文）拼进简报，防上下文爆炸。
- `execution.py:start_immediate_tasks`：删除"启动即递减"，改为**只派根任务**（无前置），有依赖的等完成事件驱动。
- `execution.py:start_task_as_conversation`：新增 `prereq_briefing` 参数，注入派发 prompt。
- `server.py:_on_task_finalized`：在 `stream_state=="completed"` 分支调用 `on_employee_task_completed`（完成钩子本就存在，零新增基础设施）。
- `tools/plans.py` + `schemas/orchestration.py`：`depends_on` 契约升级为 int/int[]。

**已验证**：A→B 串行（B 等 A 完成）；A∥C→B 多依赖汇合（B 等 A、C 都完成，简报含两者产物）；幂等（不重复派发）。

### Phase 2 · 房间数据模型
- 新增 `apps/server/src/models/group_room.py`：`GroupRoom`（房间实例：群时间线会话 + 计划 + 组长 + 状态）、`GroupRoomMember`（成员私有会话 + 角色 + 状态 + 白名单）。
- `ConversationMessage` 新增 `sender_id` / `sender_label`（仅群时间线用，解决"消息无作者字段"）。
- `models/__init__.py` 注册新模型；`db/init_db.py` 加列迁移（新表由 `create_all` 自动建，列由 `ensure_column` 幂等 ALTER）。

**已验证**：新表自动创建、新列幂等迁移、对旧库安全。

### Phase 3 · 群派发 + 投影（后端）
- 新增 `apps/server/src/service/group_room_service.py`：
  - `ensure_room`：群会话惰性建房间 + 登记成员。
  - `resolve_mentions`：解析 @员工名 / @[名] / 结构化 mentions / @全部 广播。
  - `dispatch_to_member`：把消息路由到成员**私有员工会话** + `registry.request_start`（复用 1:1 路径，零新机制）。
  - 投影：成员私有流完成 → 读其最终结论 → 写群时间线（带 sender_*）+ 经 `WorkspaceEventBus` 推 `room_message` 事件。
  - 白名单 `allow_from` 控制谁能 @ 谁。
- `chat_service.stream_conversation_answer`：新增 `group` 分支（原来 group 会落 else 报错），委派给 `GroupRoomService.handle_group_message`，SSE 返回派发回执。
- `api/group_api.py`：新增 `GET /chat/conversations/{id}/room` 返回房间状态（成员侧栏用）。
- `schemas/conversation.py`：`ConversationMessageRead` 暴露 `sender_id`/`sender_label`。

**已验证**：建房、@解析（含广播）、时间线作者归属、房间状态序列化、白名单、幂等。

### Phase 4 · 前端群聊 UI
- `hooks/use-workspace-events.ts`：事件 union 增加 `room_message` / `room_member_state`。
- `api/group-room.ts` + `hooks/use-group-room.ts`：拉房间状态 + 监听房间事件刷新时间线/成员。
- `components/chat/group/group-member-sidebar.tsx`：成员侧栏（头像 + 角色 + 状态：待命/进行中/休眠/已交付）。
- `components/chat/group/group-room-view.tsx`：群视图 = 复用 `ConversationChatView`（时间线 + @输入）+ 成员侧栏。
- `components/chat/views/chat-view.tsx`：`contact.type==="group"` 路由到 `GroupRoomView`。
- `lib/chat/chat-mappers.ts` + `api/types.ts`：消息映射读取 `sender_label`/`sender_id`，群消息显示发言人。

**已验证**：`tsc --noEmit` exit 0、ESLint exit 0。群联系人→会话→@成员→/stream 的链路本就贯通（`mapContactToTarget` 已支持 group）。

## 二、数据流（一条群消息的旅程）

```
用户在群里发 "@前端 做个落地页"
  → POST /chat/conversations/{群会话}/stream
  → chat_service 识别 target_type=="group" → GroupRoomService.handle_group_message
     ├ 写用户消息到群时间线（sender="用户"）
     ├ 解析 @前端 → 命中房间成员（白名单校验）
     └ dispatch_to_member：前端私有会话 append user + registry.request_start
  → 前端员工私有流 astream …（隔离上下文/缓存）… 完成
  → 投影器读其结论 → 写群时间线（sender="前端"）+ push room_message 事件
  → 前端 useGroupRoom 收到事件 → 刷新群时间线 + 成员状态变"已交付"
```
若是编排计划（DAG）：某任务完成 → `on_employee_task_completed` → 派依赖它的后继（附前置产物引用）。
