## C. 真实降级 / 可能回归（建议拍板）

1. ⚠️ **多计划会话只显示最新计划的交付物**（#9 + 位置调整引入）。
   交付物卡从「每张计划卡内」移到「本轮最后消息末尾页脚」，并**从计划卡移除**后：一个会话里有多个已完成编排计划时，**早先计划的交付物不再在任何地方展示**（页脚 `CuratorTurnDeliverables` 只取最新非 pending/cancelled 计划）。
   - 单计划会话（最常见）无影响；多计划长会话是降级。
   - vs 本轮之前（根本没有交付物展示）仍是净增；vs 中间版本（每计划卡各显）是回退。
   - 可选补强：页脚展示全部已完成计划的交付物，或计划卡内也保留一份。

2. ~~⚠️ **edited 文件的 size 用 new_string 长度**~~ → ✅ **已修**（commit `baed092d`）：
   交付物 size 只取 created 的 content 长度，edited 置 None（前端缺省即不显示）；created→edited 保留 create 大小。

3. **P2-A 提示词瘦身**：删掉了「禁止复述自动放行/DAG/reported_at…」的**枚举**。
   若模型偶发泄漏内部机制黑话，是轻微回归（概率低；功能性指引全保留）。

4. **P1-A 低风险单任务自动执行**：「只读」判定是**关键词启发式**；被派员工 `enable_hitl=False`，一旦误判把含破坏性操作的任务当只读自动放行，则无 HITL 拦截。
   - 保守口径（small 档 + 无 cron + 破坏性词命中即走确认）已尽量压低，但非零风险。
   - ✅ **已加代码级底线**（commit `2c9ed202`）：`command_safety.py` shell 硬底线对所有 agent（含 HITL-off 员工）生效——灾难命令（rm -rf 根、mkfs/dd 写盘、fork bomb…）**永不执行**，不靠模型/确认门遵从。注：是 floor 非完整沙箱（彻底边界需 OS 沙箱，见 [Hermes 参考 F](reference-hermes-agent-learnings.md)）。

# 第二轮：技能在用中自改进(A) + 生命周期 curator(B) 复盘

> 借鉴 Hermes 的 A/B 两条（[reference-hermes-agent-learnings.md](reference-hermes-agent-learnings.md) §二）。**与上一轮不同：A/B 走了完整正式流程**——spec(过 spec-reviewer) → plan(过 plan-reviewer) → 逐任务 subagent + 两阶段审查(spec 合规 + 代码质量) → 整体审查。后端 954 passed、前端 tsc 净。下面诚实记录妥协。

## G. 有意的 v1 范围收窄

| 项 | 收窄点 | 留待 |
|----|--------|------|
| A 信号源 | v1 只把「用户低分反馈」自动接入技能修订线索；**返工/失败信号未自动定向到具体技能**（仍只进 memory） | v1.1：reflection 已有 rework 检测，缺「关联到具体技能并注入」的接线 |
| B 员工归档 | 闲置 90 天只产**只读建议**，不自动归档 | 设计如此（员工归档牵动总管路由，留用户决断），非偷工 |
| B 近重复合并 | 阈值 0.8/token 集相等，**宁漏勿误并** | 保守，可按需调松 |

## H. 靠模型遵从 / 判断（非代码强制）

- **A 何时该改技能**：agent 自行判断「技能错/缺/过时且非一次性特例」才调 `update_skill`，纯提示词引导（§4.3），模型可能误判乱改或该改不改。代码侧只兜**安全**（守卫只能改已加载技能、备份、审计、回滚），不兜**判断质量**。
- **A 改成什么内容**：new_content 全由模型产出，无质量校验（只校大小上限）。错改的兜底是「人能在面板看见审计 + 一键回滚」，非「阻止错改」。

## I. 真实降级 / 需拍板的取舍

1. **A 直接改无审核门**（用户明确选「直接改+落库」而非「候选+人采纳」）：一次错改**立即传播到所有持有该技能的员工**。已用 **改前备份 + 审计成长面板可见 + 一键回滚 + 加载守卫** 四层兜住即时性风险，但**不阻止**错改本身。vs A 本可走的「候选制」（同 promote_skills，人采纳才生效）是更稳但更慢的另一条路——按用户取向选了快。
2. **B last_used 偏保守是结构性妥协**：`TaskExecutionLog.skill_id` 只记**派单技能**，prerouter 软提示/agent 自读用的技能**不落 log** → 这类「常被用但很少作为派单技能」的技能 last_used 偏旧、可能被误判闲置。已用「分配时间为基线 + SkillRating 补充取 max + 30/90 天宽阈 + archived 仅逻辑隐藏可恢复/可 pin」层层缓解——**宁可不归档，误判也一键可逆**。但根治需让「实际加载技能」也落使用流水（v1.1）。

## J. 整体审查（whole-feature）抓到、单任务审查漏掉的闭环缺口（均已修）

- **A**：① 审计 `skill_edits.jsonl` 一度自己又成「写了没人读的死文件」——违背 spec「显式可见」，已补成长面板 payload + 前端「技能修订记录」；② 低分线索 `skill_hints/` 改好后不清除 → 反复诱导改已修好的技能，已补「成功后删 hint」；③ `.history` 随 copytree 泄漏进员工副本/详情/导出，已加 `ignore_patterns`。
- **B**：① 缺「restore 抗重归档」与「archived 排除 available_skills」的端到端集成测试（单测覆盖纯函数但没覆盖闭环），已补；② 前端 restore/pin 的 TS 返回类型与后端不符（运行时无害），已修。
- 教训重申：**单任务两阶段审查保「每块对」，但「拼起来闭环是否真的合上」要靠整体审查**——A/B 各有 2-3 处只在整体视角才暴露。

## K. 测试覆盖妥协

- **前端两处均 tsc + 人工验收，无组件/渲染测试**（A 的技能修订记录；B 的 archived 折叠/恢复/置顶/归档建议）——沿用本季前端口径。
- **A `get_agent` 端到端**未单测（起真模型/检查点过重）；B 的 archived 排除以「镜像 employee.py 过滤表达式」的数据路径测试替代，非真起 agent。
- **人工冒烟尚未执行**（需 Electron + 真员工/工作区）：A 的全员同步/内置 fork 不动全局/回滚；B 的老化→隐藏→恢复/候选合并/员工建议——是两功能正确性的必要验收，待用户跑。

## L. 流程（对比第一轮的提升）

- 本轮**主动走全套正式流程**（spec/plan 双评审 + 逐任务两阶段 + 整体审查 + 文档同步），比第一轮「精简流程（§F）」严格得多；安全敏感点（A 直接改、B 路径穿越/employee_id 404）均经独立审查并修掉真实漏洞（路径穿越 Critical、备份污染内置、静默假同步等）。
- 代价：流程更重、子代理调用更多。收益：闭环缺口与安全洞在合并前被堵，而非事后 debug。
